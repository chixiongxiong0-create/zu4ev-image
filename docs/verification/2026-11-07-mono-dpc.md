# Mono RAW10 DPC 实施与验证（2026-11-07）

已实现按确认坐标修复的 DPC，通过布线和 RAM 上板验证。板卡当前以 RAM 镜像运行，FFC 和 DPC 均启用，AE 已恢复。QSPI 未改动，BOOT_MODE 已回到物理 QSPI 的 `0x2`，重启会恢复原 NV12 固化版。

用户确认的目标是保留真实单像素亮点，修复已确认坏点和小范围连续坏点。DPC 不根据视频内容的亮度自行删除像素；表外数据在 DPC 级逐位保留。顺序为 RAW10 → FFC → DPC → AE/BLC/LTM → TNR → NV12/VCU。

表容量 1024 个水平连续段，每段 1～32 像素。正常情况下用该段两侧的表外像素做线性插值；图像边缘用一侧。二维坏点簇逐行处理，不把表内坏点当作供体。超过 32 像素的连续段或没有正常邻点的整行拒绝加载。复位旁路，非活动表上传和读回后，在输出帧首切换。视频每时钟两像素，无新时钟域和 A53 逐像素处理。

- RTL：`platform/zu4ev/isp/dpc/{dpc_raw10,dpc_probe}.sv`；ISP 集成：`isp_capture_frontend.sv`、`ltm/isp_axi_regs.sv`。
- 控制、标定：`platform/zu4ev/software/isp-control/dpcctl.c`、同目录 Makefile、`platform/zu4ev/isp/dpc/make_map.py`。
- RAM 打包：`platform/zu4ev/boot/package_ffc_ram.py` 增加可选 `--dpcctl`。接口、流程见 [DPC 使用说明](../../platform/zu4ev/isp/dpc/README.md) 和 [设计](../../platform/zu4ev/isp/dpc/DESIGN.md)。
- 定向测试：`tests/zu4ev/dpc/`。

验证结果：

- 1280×1024 全尺寸五帧，逐对参考比较 **3,276,800 对像素**，seed `d9c01234`。覆盖 1～32 像素坏段、两种起始 lane、二维簇、行首/行尾/帧尾、真实孤立亮暗点、随机空拍、相邻帧、1024 段满表、在线换表、坏帧恢复和复位。
- 候选采集验证双 lane、恰满容量、溢出不发布、畸形帧不发布、恢复和低阈值采集。
- 真实 ISP 前端的 AXI 定向联调验证 FFC/DPC 地址切换、AW/W 独立顺序、B/R 停顿、非法写、寄存器响应稳定，以及校正前后探针只移除表内的亮点。此测试用 LTM 观测替身，完整 LTM/视频链路以实际工程和板测为准。
- FFC 现有 AXI 回归、主机地图生成四项测试、C 工具五种非法地图预检和 ARM 静态编译通过。
- ZU4EV 完整工程综合、布局、布线、DRC、bus skew 和 bitstream 生成通过。最终建立 WNS **+0.107 ns**、保持 WHS **+0.010 ns**，TNS/THS 为 0。全工程 LUT 62,952（71.67%）、BRAM 116.5（91.02%）、URAM 36（75%）、DSP 98（13.46%）；DPC 候选 RAM 增加 2 个 BRAM36，坐标表映射为分布式 RAM。

项目在 `build/dpc/project/dpc.xpr`，由已验证的 FFC 工程复制并重新综合、实现。首次实现因未复制匹配的 DDR4 PHY IP 缓存而失败；复制原 FFC 的 `7611e373eaada90e` 和 `0f9561fc05b9273b` 缓存后重跑通过，未修改 DDR4 配置或时钟约束。实际报告在 `build/dpc/route_reports/`，仿真与板测证据在 `build/dpc/`。

## 真实暗场坏点

保持完全遮黑。启动设置下用 RAW10 阈值 80 和 72 各进行两批 64 帧，均无坐标达到两批各 61 帧。允许 AE 在遮黑条件下稳定后停止并回收 PS 所有权，曝光和增益保持不变。该设置下，RAW10 网格均值 49.60～60.88；阈值 128、96、80 均无满足规则的坐标。阈值 76 下，两批各 64 帧只有 **(1021, 472)** 同时达标，原始命中分别 64/64 和 62/64。坐标以左上角为零起点，最终表只有一个长度为 1 的段。没有将未达标的偶发高亮写入表。

同一 FFC 表、同一冻结设置、同一 RAW10 阈值 76，切换 DPC 测量该坐标：

| DPC 状态 | 该坐标 ≥76 的帧数 | 硬件每帧修复计数 |
|---|---:|---:|
| 初始旁路 | 57/64 | 0 |
| 启用 | 0/64 | 1 |
| 再旁路 | 62/64 | 0 |
| 再启用 | 0/64 | 1 |

只读 PS I²C 在 AE 停止后的两次元数据查询超时，未改变 sensor 寄存器。启动阶段 PS 读回正常。Ibex 诊断邮箱在后续读取显示曝光 `0x20d0`、增益字段 `0x3f`；这不是逐项 PS I²C 读回。已用实际两批调查文件和 `make_map.py --require-all-surveys` 重新生成地图，逐字节等于板上已加载的表。没有在本机发现符合判据的连续坏点簇；连续段能力由 RTL 仿真验证。冷坏点没有在本次遮黑标定中确认，需要均匀亮场或已确认坐标。

## 视频回归与 AE 恢复

- `nv12_vcu_probe`：2400 帧、27,600,123 编码字节、20,149.067 ms，约 119.11 fps。
- USB 主机两次开流：35.306 秒解码 4016 帧、35.294 秒解码 4024 帧，格式 H.264、1280×1024、yuv420p。第二轮关闭附近记录 1 次 `USB_ERR_BUFFER`，随后 STREAMOFF。最终 `invalid=0`，USB ownership/DQ/event/send 错误为 0；发送 8347、回收计数 8346，不能宣称整个会话零错误或计数完全相等。DP/采集仍推进。
- 首次 AE 启动正常；标定后再次接管复现既有 store trap（`mcause=7`、`mepc=0x0010061c`）。PS 安全回收后用 VIO 只复位 Ibex，验证 FFC/DPC 表保留，再恢复 AE。随后 mailbox `state=3`、`fault=0`、`signature=600dae01`，记录约一秒增加 124。固件握手问题本次仅恢复运行，没有更改或修复。
