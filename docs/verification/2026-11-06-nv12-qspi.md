# NV12 QSPI programming and board verification — 2026-11-06

QSPI programming and reset boot succeeded. NV12/VCU and host USB decode passed.
Whole-system acceptance is **blocked by an Ibex AE startup fault**. Physical
power-off/power-on has not been tested. No RTL or firmware source was changed.

## Reset boot and video results

BOOT_MODE override restored from `0x2102` to physical QSPI `0x2`. XSDB system
reset stopped at BootROM and was continued. Production FSBL read QSPI partitions,
configured PL, and reported `SENSOR_READY`. U-Boot read 20 MiB at flash offset
`0xc00000` and verified FIT component hashes. Linux booted and exposed
`/dev/sc130-nv12`; runtime configuration enables PL NV12 and H.264.

- `nv12_vcu_probe 2400`: PASS, 18,198,445 coded bytes, 20,174.738 ms (~118.96 fps).
- DirectShow USB receive/decode: 4015 decoded frames, 4134 packets,
  45,109,299 bytes over 35.294 s including startup/shutdown.
- Decoded format: H.264, 1280x1024, yuv420p.

## AE failure and acceptance limit

After reset, handoff reported owner=1, run=1, quiescent=1, armed=0, fault=1.
Read-only JTAG AXI mailbox inspection found state=5 (AE_FAULT), fault=10
(AE_TRAP), mcause=7 (store access fault), mepc=`0x0010061c`, IRQ=0,
records=0, signature=0. This means AE did not enter live frame processing.

Disassembly of the matching `build/ibex_small/ae_live/ae_live.elf` maps that PC
to the waiting-loop write of 4 to sensor firmware CSR `0x5200001c`.
The firmware separately reads RUN then writes quiescence. RTL accepts that
write only with RUN low. A RUN transition between the read and write is a
plausible race explaining the trap; the precise transition was not captured.
This diagnosis must be verified by a focused handshake regression before a fix
is accepted. Do not describe this image as a fully accepted final flash release.

Evidence files: `preflight.log`, `backup-uart.log`, `flash-verify.log`,
`qspi-boot.log`, `post-boot.log`, `ae-diag.log`, `ae-mailbox.txt`,
`usb-capture.json`, `usb-nv12.h264`, and `final-health.log`.

## User physical restart follow-up

The user physically restarted the board after the reset-boot test. Read-only
inspection shortly after Linux startup found owner/run/grant/armed=1,
quiescent=0, fault=0 on both samples. JTAG mailbox state=3 (AE_RUNNING),
fault=0, signature=`600dae01`; IRQ advanced 2742 to 2863 and records advanced
2742 to 2864 over approximately one second. AE is actively processing frames
on this physical boot. Capture and DP counters advanced at approximately
120 fps, invalid=0, USB errors=0. No host stream was active during this check,
so this physical boot has not separately repeated the prior USB decode test.

The earlier startup trap did not reproduce on this one physical restart.
No firmware/RTL fix was applied, so the earlier failure and suspected handshake
race remain unresolved rather than proven fixed. Evidence:
`physical-reboot.log` and `physical-reboot-mailbox.txt`.
